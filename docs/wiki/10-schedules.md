# 10 Schedule

## 已确认的职责 `开发中`

2026-10-27，用户确认：

> agent拥有一个布置schedule任务的工具，时间到了之后，任务的上下文会发给main

Agent 通过工具保存安排，到期后系统把任务上下文投递给该用户的 Main。Main 沿用长期对话和现有执行工具处理输入，可以直接工作，也可以派发 Subagent。选择理由是让未来任务复用 Main 的理解、执行与沟通能力。Schedule 负责时间和上下文投递。

用户随后确认按此方案直接实现，一次性和周期任务都支持。当前已有工具、数据表和调度代码，实现采用下面的投递与恢复规则。

## 工具与任务上下文

Main 与 Subagent 共用 `schedule` 工具，支持 `create`、`list`、`update` 和 `delete`。`update` 的 `enabled=false` 暂停，`enabled=true` 恢复。用户归属从调用者身份取得，触发目标固定为该用户的 Main。列表每页最多 50 条，使用返回的 `next_before` 读取下一页。

创建时由 Agent 整理任务说明和必要背景，保存一份未来仍能理解的上下文，包括目标、资料位置、限制和交付要求。完整历史仍保留在 Main 的长期对话中，无需默认复制整段聊天。不能依赖“处理刚才那个”这样的临时指代，也不能把搜索结果中的指令当成用户授权。

一次性安排使用带明确 UTC 偏移的 RFC3339 `at`，周期安排使用五段 `cron`，两者互斥。创建时必填 `timezone`，接受 `Asia/Shanghai`、`UTC` 这样的明确时区，拒绝依赖宿主配置的 `Local`。周期规则不接受秒字段和 `@every`。工具返回实际保存的规则、时区、上下文和下一次触发时间。Agent 只有拿到成功回执后才能确认已安排。标题最多 160 字符，上下文最多 24,000 字符。

例如，每个工作日北京时间 9 点的安排使用以下参数：

```json
{
  "action": "create",
  "title": "工作日项目公告",
  "context": "检查用户指定项目的官方公告，整理重要变化和来源链接后告诉用户。项目链接与筛选标准须在创建时补全。",
  "cron": "0 9 * * 1-5",
  "timezone": "Asia/Shanghai"
}
```

运行时在每次模型请求中提供当前 UTC 时间，供 Agent 计算相对日期。用户时区未知且影响安排时，Agent 需要先澄清，不使用服务器时区猜测。

## 到期如何进入 Main

当前 `Runner.Start` 在启动时和每秒扫描数据库队列，待读消息会唤醒对应 Agent。执行锁保证同一用户的 Main 串行工作。Schedule 可以复用这些能力，相关代码在 `backend/internal/agent/runner.go` 和 `backend/db/queries/messages.sql`。

调度器在启动时及之后每秒扫描，按以下流程投递：

1. 从数据库扫描到期候选。
2. 开启短事务，先取得该用户的消息写锁，再锁定计划行，重新检查状态、版本和到期时间。
3. 使用数据库时间，写入本次触发记录和发给 Main 的待读消息。
4. 周期计划计算下一次时间，一次性计划标记为已触发。
5. 在同一事务发出通知并提交，随后唤醒现有 Runner。

触发消息包含计划 ID、本次触发 ID、原定时间、实际投递时间和上下文快照。沿用 `role=user`、`sender=system`、`sequence=NULL` 的内部消息形态，并在内容中注明来源。`sender` 表示消息来源，模型消息的 `role` 表示输入形态，两者不能混为一谈。

现有聊天查询隐藏这类内部输入，Main 仍以正文联系用户（2026-10-30 起取代 `send_message(to=user)`）；不写正文即静默处理完本次触发。Main 正在工作时，新输入在后续模型请求前读取，不中断正在进行的请求。

## 持久化与恢复

`schedules` 保存用户、标题、任务上下文、时间规则、时区、状态、版本和 `next_run_at`。状态为 `active`、`paused` 或 `triggered`，最后一种仅表示一次性安排已投递，不表示任务执行成功。`schedule_occurrences` 保存本次上下文快照、原定时间、投递时间和触发消息 ID，并以计划、版本、原定时间的组合建立唯一约束。

触发记录、待读消息和下一次时间必须在同一事务提交。这样进程中途退出时，要么整次投递提交，要么留待下次扫描。内存中的 timer 和通知只负责唤醒，PostgreSQL 保存事实。创建、修改和删除计划也放在现有 `executeDatabaseTool` 事务内，与工具回执一起提交。

现有 `saveReply` 先取得用户消息写锁，再执行数据库工具。调度器必须遵循相同锁顺序，避免修改计划和触发计划互相等待。等待未来时间不占 Agent 执行锁或模型请求。

本次记录只证明上下文已投递给 Main。`steps.finished_at` 表示某个模型步骤结束，不能证明整个任务完成，Main 还可能等待 Subagent。首版无需因此新增通用任务或工作流实体，也不能承诺外部操作恰好执行一次。

## 漏跑、暂停和删除

一次性安排在服务恢复后补投递。周期安排将尚未投递的时间合并成一次投递，记录最早未投递的原定时间和实际时间，再从当前时间计算下次触发。这样恢复后不会逐次补跑并挤占 Main。正常周期仍按当地日历计算，不从任务结束时间累加。夏令时跳变沿用 cron 库规则。

暂停和删除只影响未来触发。删除计划会级联删除触发记录，已经投递的消息和上下文仍保留在 Main。暂停后恢复周期安排会计算下次未来时间；恢复已经过期的一次性安排需要同时设置新的 `at`。修改标题或上下文不改变下一次时间，历史触发保留原快照。

固定间隔安排不属于此次实现。无变化时静默结束自 2026-10-30 起已可达：Main 回复用户改走正文后不再有针对 Main 的交付检查，不写正文即合法沉默，静默监控无需再等单独的完成协议。

后台执行与设备通知分开。Android 当前没有系统推送，因此保存结果和重连补消息不能等同于关闭 App 后弹出系统提醒。
