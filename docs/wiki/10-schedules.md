# 10 Schedule 与闲置反思

2026-11-08，用户重新加入两项能力：Main 用 `schedule` 工具设置定时任务，以及系统在对话闲置后定时请 Main 回看历史、自行决定此时做些什么（整理记忆、给出用户没想到的观察等）。两者共用一套机制：后台调度器到点往该用户的对话里插入一条不可见的 user 消息，再唤醒 Main。本地开发中，未推送部署。

## 运行机制

**触发消息。** 定时任务与反思都以 `role = user`、`sender = system`、`visible = false` 的消息写入 `messages`，用 `content.name` 区分：`schedule_event`（定时任务）与 `reflection`（闲置反思）。Main 是否有活只看消息尾部（视图 `main_work`），最后一条是 user 消息即有活，所以 agent loop 的三个阶段与循环主体都不需要知道“定时”这回事：触发消息照常进入请求组装、思考中被新输入打断、压缩进摘要。插入后调度器调用进程内 `Manager.Wake` 唤醒 Main（`00040` 起不再有数据库触发器）。

**调度器。** `backend/internal/scheduler/` 由 `main.go` 启动，每 5 秒扫描一次到期安排与到期反思，失败在这一层记录日志，未投递的下一次扫描再试。触发精度因此在 5 秒量级。

### 定时任务

- 表 `schedules`（`00045`）：标题、到点时交给模型的上下文、可空的 `cron` 与 `timezone`（两者同时为空即一次性）、`next_run_at`。
- 工具 `schedule` 支持 `create`、`list`、`update`、`delete`，与回执同一事务提交。`update` 只改给出的字段：给 `at` 变为一次性，给 `cron` 变为周期，只改标题或上下文时保持原触发时间。参数错误返回工具错误，让模型自行修正（过去的时间、缺时区、非五段 cron、未知时区等）。
- 投递在一个事务里完成：取用户消息锁、锁定这条到期安排、插入触发消息、删除一次性安排或把周期安排推进到下一次。两步同时提交，所以不会出现消息已投而安排未推进、被下次扫描重复投递的情况；扫描之后被模型改到未来或删除的安排不再投递。
- 周期安排从投递时刻往后计算下一次，停机期间错过的多次触发合并成一次投递；触发消息里附原定时间 `scheduled_for` 与实际投递时间 `delivered_at`，由模型考虑延迟。
- 一次性安排投递后即删除，原上下文保留在触发消息里。
- 模型只能拿到 UTC 时间标记，数据库没有用户时区；固定指令要求模型从记忆中找用户时区，不知道且有影响时询问。

### 闲置反思

- 到期条件（查询 `ListReflectionDue`）：最近一条用户本人的消息之后还没有 `reflection` 消息、Main 没有活、对话最后一条消息（含助手回复与工具回执）已闲置满设定时长。所以闲置从 Main 处理完开始计时，每段新对话只反思一次；定时任务与反思自身产生的消息不算用户消息，不会反复触发。
- 最近一条用户消息早于“闲置时长再加一天”的不触发：上线或停机恢复后，不给很久以前的对话补跑反思，避免公开实例上大量旧用户同时产生模型调用。这是实现时的技术判断。
- 投递事务在用户消息锁内按同样条件复查，扫描之后刚好收到新消息的用户不再投递。
- 闲置时长保存在 `model_settings.reflection_idle_minutes`（`00046`），每次扫描现读，看板修改后下一次扫描生效。反思由 Main 模型执行。
- 反思指令（2026-11-09 版）分三步：对照记忆根与相关主题回看近期对话，补存遗漏并更新对用户的理解；私下列几条候选（接着近期话题的补充、风险、下一步，或基于理解推荐用户没接触过的新东西），优先针对本人、对他新、实际有用的，需要时联网找具体的现有资源；读推荐记录 `/memories/topics/suggestions.md`（不存在就创建并在根索引加链接）去重，写正文前先把选中的点连同日期追加进去，近期对话里看得出用户对旧推荐的反应时一并记下。默认倾向发一两条简短跟进，只有确实没有有用的候选时才不写正文。仍然不登记任务、不改任务状态、不继续或重做旧工作。Main 不写正文即不推送消息，这条路径原本就存在，不需要额外机制。
- 推荐记录只在反思时读写，平时对话的建议不写入，固定指令不变；记录文件走现有 `memory` 工具，后端不需要新机制。写正文就结束本轮，所以记录必须在写正文之前更新。

### 提示词

固定指令新增一段：何时使用 `schedule`、上下文要写成未来自己能独立执行的说明、时间须带偏移或 IANA 时区；`schedule_event` 与 `reflection` 都不是用户本人的新消息。`schedule_event` 正文说明：需要实际工作的按用户请求先用 `record_task_input` 登记，简单提醒可直接用正文送达。反思与定时触发的文案集中在 `backend/internal/agent/prompt.go`。

## 已知影响

- 反思运行后若仍有进行中或排队的任务，Runner 现有的收尾任务提醒（见 [11](11-tasks.md)）照常会在同一次运行里续跑一轮。长期不更新状态的任务因此可能在每次反思后多一轮请求。
- 管理看板的模型配置页新增“闲置反思”分组；工具统计识别 `schedule`。

## 本地验证（2026-11-08）

`00045` 与 `00046` 在本地 PostgreSQL 18 完成执行、回滚、再执行；Go 构建、`go vet` 与看板构建通过。用真实后端与 ikun Gemini 模型验证：已到期的一次性安排与逾期三天的周期安排各投递一次，一次性安排被删除，周期安排推进到下一个上海时间 9:00，Main 收到后回复并说明了延迟；`schedule` 工具的创建、修改、列出、删除与各类参数错误均按预期返回。闲置反思在测试对话闲置后投递一次，Main 读取记忆根、新建个人生活主题并更新索引，随后不写正文结束，没有推送消息或记为失败；之后持续扫描未再次触发。没有新增测试文件，测试数据已清理，没有推送或部署。
