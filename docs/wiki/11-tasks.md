# 11 需求队列 `开发中`

2026-11-06，用户要求增加 tasks 表和工具：

> 当模型收到一个需求的时候，用 tasks 登记这个需求，如果收到用户后续的补充说明，更新这个需求。
>
> 如果模型在完成一个需求的时候，收到了用户的另外一个需求，就先登记这个需求然后继续完成当前任务，完成当前任务了之后再去读取 tasks 表来完成任务，即一个阶段只做一件事情。

因此，用户需求持久化到 `tasks`，Main 每次只执行一个目标。这取代 [05 Main 运行时](05-main-runtime.md#连续消息与多个请求2026-11-04) 中只靠提示词追踪未完成需求的方案。任务仍由同一个 Main 执行，每个用户继续使用同一份长期对话。

## 登记与执行分开

用户消息先按原有流程存入 `messages`。Main 在安全的模型决策边界读取下一条尚未登记的输入，判断它与已有任务的关系。同一目标的背景、限制和修正更新原任务；不同目标分别创建排队任务。一条消息可以更新多项旧任务，也可以创建多项新任务。

登记阶段只开放 `list_tasks` 与 `record_task_input`。后者一次提交这条消息的全部任务变更，并推进 `users.task_input_through_sequence`。变更、输入登记位置与工具回执在同一个事务里提交，崩溃时一起回滚。重跑时跳过已有回执，重复登记旧消息也不会重复创建任务。

选择单独保存输入登记位置，是因为“消息已经分类”和“需求已经完成”是两件事。B 已经排队时，Main 可以继续处理 A，同时准确知道 B 的原始输入不必再次登记。这个位置只用于需求分类，不是聊天已读回执。

没有待登记输入后，Runner 读取当前任务。已有任务时继续执行；没有当前任务且有 `queued` 待办时，进入模型选择阶段。后端只提供 `needs_task_selection` 标记，不替模型选取任务。

2026-11-06，用户纠正此前“先登记先做”的实现假设，并明确选择“由模型读取 tasks 自行选择下一项”。据此，模型先调用 `list_tasks`，根据用户需求与任务上下文选择一项待办，再单独调用 `update_task(task_id, status="in_progress")` 启动。工具列表的显示顺序、任务 ID 和创建时间不构成执行优先级。删除 `source_sequence`（`00039`）的决定保留；UUIDv7 ID 只用于标识和稳定展示，不再由后端按 ID 自动领取。

选择阶段只开放 `list_tasks` 和 `update_task`，不发送用户可见正文；启动提交后，下一轮请求才按所选任务开放执行工具。数据库部分唯一索引保证每个用户最多一项 `in_progress`。待办启动要求没有当前任务、没有尚未登记的输入；已有任务不能被另一个任务抢占，等待、完成和取消项不能由模型直接重新启动。

例如，A 正在执行时收到 B，再收到“把 A 讲给初学者听”，Main 先登记 B，再把补充合并到 A。登记完成后，Main 继续按更新后的要求完成 A，A 结束后，模型再读取任务列表选择下一项。A 执行期间，模型不能把 B 提前改为执行中。

## 任务记录与工具返回

2026-11-06，用户要求将任务记录的两个来源字段改为 `related_message_ids`，删除 `outcome`，并去掉 `list_tasks` 的 `task_id` 参数。

任务快照返回 `id`、`title`、`description`、`status` 和 `related_message_ids`。`task_messages` 只保存提出需求和后续补充的用户输入，每次登记时追加并去重；读取时按消息序号返回 ID。助手回答、进度与文件不加入关联列表，任务没有结果字段。

`list_tasks` 只接收可选的 `include_closed`，始终返回最多 100 项任务的数组。`record_task_input` 返回本次变更的任务数组，`update_task` 返回更新后的单个任务；它既能在空闲时启动模型选择的待办，也能完成或暂停当前任务。登记工具的 `source_message_id` 仍用于指定本次待登记消息，不是任务记录的返回字段。

## 只管理任务，不绑定产物

2026-11-06，用户决定先去掉所有任务与产物绑定，只保留任务记录的创建、读取、更新与状态管理。理由是先把需求登记和逐项执行做好，产物归属以后再讨论。

任务工具只保留 `list_tasks`、`record_task_input`、`update_task`。不提供结果追加工具、不建立结果表；助手消息和文件都不保存任务归属。`task_messages` 继续关联用户需求和补充来源，这是输入追溯，不是产物绑定。取消通过状态 `cancelled` 表示，不新增物理删除工具。

迁移 `00041_remove_assistant_task_binding` 删除旧 `messages.task_id`、相关索引和“可见助手消息必须有任务”的约束。历史消息正文、任务与输入关联继续保留；Down 只恢复旧结构，不猜测已经移除的回答归属。聊天实时与历史接口、前端消息类型也不再包含任务 ID。

登记与任务选择阶段仍只调用工具，不发送正文；其他正文作为独立聊天消息保存。模型继续按当前任务聚焦工作，但后端不把回答登记为任务结果，也不做产物交付检查。

## 任务怎样结束与恢复

Main 使用 `update_task` 变更当前任务的状态，入参只有 `task_id` 和 `status`。模型判断要求的工作已经完成后，将状态改为 `completed`。这个操作只更新任务记录，不绑定回答或文件，也不要求先登记任何结果。进度和等待原因保留在对话中，任务表不设置 `outcome`。内部工具回执、进度消息或状态变更本身不代表结果已经交付。

需要用户澄清或外部条件暂时不满足时，Main 先说明原因并提出必要问题，再将任务标为 `waiting`，保留恢复所需的信息。其他排队任务可以继续。用户补齐条件后，登记工具将对应任务重新排队。用户明确取消时才标为 `cancelled`，新话题本身不取消旧任务。这延续此前关于受阻任务和取消语义的选择。

启动、完成或等待的 `update_task` 仍由工具说明要求单独占一批工具调用，但 2026-11-06 用户确认删除运行时的执行前批级拦截（原 `taskBatchRestrictions`）：登记与选择阶段已按阶段限定下发的工具范围，状态合法性由 `UpdateTaskStatus` 的 SQL 条件与单活动任务唯一索引保证；混批从未在真实模型上观察到，此前仅用受控脚本响应验证过拦截，保留它属于针对未发生情况的重复防御。工具批次执行期间到达的新输入不打断已发出的批次，在下一次模型决策时登记。

`main_work` 同时检查消息尾部、尚未登记的用户输入，以及 `queued` 或 `in_progress` 任务。一次正文回复结束不再等于全部需求结束。Runner 在每次模型请求的历史末尾注入 `task_context`，提供当前任务、下一条待登记消息的原文和是否需要模型选择任务的标记。任务表是当前状态，历史工具快照与 compact 摘要不能覆盖它。任务快照只放在尾部，不改写已保存的消息历史。尚未登记的原始消息若已被 compact 移出当前世代，运行时会额外补回其原生内容，保留图片内容块。

模型调用失败仍沿用 `main_failed_through_sequence` 停住自动重试，任务、关联消息与对话历史保留；有新输入时再次处理。2026-11-06 起，进程崩溃后的恢复改由启动与五秒补偿扫描推进，按健康实例容量重新分配；不再需要等待用户发送下一条消息。任务是否可运行仍以 `main_work` 和失败停住位置为准，见 [12 Agent 多实例路由](12-agent-routing.md)。

## 实现取舍

目标归类需要理解用户语义，因此仍由模型判断。数据库保证单任务状态与事务提交，Runner 保证单任务执行与登记、选择阶段的工具范围；这些约束不能证明模型对“同一目标”的判断一定正确，也不能判断回答内容是否真正满足需求。

登记通常增加一轮模型工具调用。任务状态在请求尾部变化，登记和执行阶段的工具定义也不同，供应商的缓存命中情况需要另行观察。选择这一成本，是为了把未完成需求从容易遗漏的对话推断变成可恢复的持久记录。

迁移 `00034_add_tasks` 跳过最后一次普通助手收尾之前的历史输入，只登记其后尚未处理的用户消息，不回填全部历史需求。表结构见 [02 数据模型](02-data-model.md#tasks)，工具登记位于 `backend/internal/agent/tools/tasks.go`，运行时接入位于 `backend/internal/agent/tasks.go`。
