# 11 需求队列 `开发中`

2026-11-06，用户要求增加 tasks 表和工具：

> 当模型收到一个需求的时候，用 tasks 登记这个需求，如果收到用户后续的补充说明，更新这个需求。
>
> 如果模型在完成一个需求的时候，收到了用户的另外一个需求，就先登记这个需求然后继续完成当前任务，完成当前任务了之后再去读取 tasks 表来完成任务，即一个阶段只做一件事情。

因此，用户需求持久化到 `tasks`，Main 每次只执行一个目标。这取代 [05 Main 运行时](05-main-runtime.md#连续消息与多个请求2026-11-04) 中只靠提示词追踪未完成需求的方案。任务仍由同一个 Main 执行，每个用户继续使用同一份长期对话。

## 登记与执行分开

用户消息先按原有流程存入 `messages`。Main 处理一条用户消息时先用 `record_task_input` 登记它，判断它与已有任务的关系。同一目标的背景、限制和修正更新原任务；不同目标分别创建排队任务。一条消息可以更新多项旧任务，也可以创建多项新任务。

三个任务工具与全部其他工具一起在每次请求中开放，登记、选择与执行的先后只由固定指令约束，后端不再按阶段缩小工具范围。`record_task_input` 一次提交这条消息的全部任务变更，并推进 `users.task_input_through_sequence`。变更、输入登记位置与工具回执在同一个事务里提交，崩溃时一起回滚。重跑时跳过已有回执，重复登记旧消息也不会重复创建任务。

选择单独保存输入登记位置，是因为“消息已经分类”和“需求已经完成”是两件事。B 已经排队时，Main 可以继续处理 A，同时准确知道 B 的原始输入不必再次登记。这个位置只用于需求分类，不是聊天已读回执。

当前在做哪个任务、队列里还有什么，由模型在需要时自己调用 `list_tasks` 读取；后端不在请求前替它查，也不替模型选取任务。

2026-11-06，用户纠正此前“先登记先做”的实现假设，并明确选择“由模型读取 tasks 自行选择下一项”。据此，模型先调用 `list_tasks`，根据用户需求与任务上下文选择一项待办，再单独调用 `update_task(task_id, status="in_progress")` 启动。工具列表的显示顺序、任务 ID 和创建时间不构成执行优先级。删除 `source_sequence`（`00039`）的决定保留；UUIDv7 ID 只用于标识和稳定展示，不再由后端按 ID 自动领取。

启动任务时，固定指令要求模型单独调用 `update_task`，不发送用户可见正文；启动的工具回执进入历史后，模型才开始执行。工具定义不随阶段变化。数据库部分唯一索引保证每个用户最多一项 `in_progress`。待办启动要求没有当前任务、没有尚未登记的输入；已有任务不能被另一个任务抢占，等待、完成和取消项不能由模型直接重新启动。

例如，A 正在执行时收到 B，再收到“把 A 讲给初学者听”，Main 先登记 B，再把补充合并到 A。登记完成后，若 B 并不比 A 更该先做，Main 继续完成 A，A 结束后再选择下一项。若模型判断 B 该先做，则先把 A 改回排队，再启动 B；A 仍为执行中时不能直接把 B 改为执行中。

## 先做更该先做的事（2026-11-09）

2026-11-09，用户要求模型自己决定先做优先级高的事情。仍是一次只做一件事，不新增优先级字段，列表顺序、任务 ID 和创建时间仍不构成执行优先级。新需求登记之后，模型判断它是否该先于当前任务：该先做时，用 `update_task` 把当前 `in_progress` 改回 `queued`（单独一批、无正文），下一轮再单独把选中的排队任务标为 `in_progress`；当前任务仍该先做完时，继续做它。只因来了新消息就切换，不符合这条规则。

`waiting` 仍表示卡在用户澄清或外部条件上，不表示先去做别的。搁下用 `queued`，收尾提醒仍会把它算进未完成任务。提醒原文也改成：进行中的工作若该让位，先改回排队，下一轮再启动更该先做的那项；没有进行中任务时，选择该先做的排队任务。登记工具不能把进行中的任务改回排队，那次改状态只走 `update_task`。

数据库不用新迁移。`UpdateTaskStatus` 在当前行已是 `in_progress` 时不限制新状态，`tasks.status` 的 CHECK 本来就包含 `queued`；原先挡住房下的是工具入参只接受 `in_progress`、`completed`、`waiting`。启动另一项的条件不变：该行必须是 `queued`，且这个用户没有别的 `in_progress`。同一批工具调用并行执行，搁下和启动放在同一批时，启动仍会看到旧的进行中任务而失败。固定指令要求这两步分成两轮，不恢复此前已删除的批级拦截。

## 任务记录与工具返回

2026-11-06，用户要求将任务记录的两个来源字段改为 `related_message_ids`，删除 `outcome`，并去掉 `list_tasks` 的 `task_id` 参数。

任务快照返回 `id`、`title`、`description`、`status` 和 `related_message_ids`。`task_messages` 只保存提出需求和后续补充的用户输入，每次登记时追加并去重；读取时按消息序号返回 ID。助手回答、进度与文件不加入关联列表，任务没有结果字段。

`list_tasks` 只接收可选的 `include_closed`，始终返回最多 100 项任务的数组。`record_task_input` 返回本次变更的任务数组，`update_task` 返回更新后的单个任务；它既能在空闲时启动模型选择的待办，也能完成或暂停当前任务。2026-11-07 起（`00043_unbind_tasks_from_messages`）任务与消息解绑：删除 `task_messages` 与 `users.task_input_through_sequence`，任务快照不再返回 `related_message_ids`，`record_task_input` 也不再接收 `source_message_id`。2026-11-08 起请求组装不再删除旧历史里的这两个字段，模型照旧例多传的 `source_message_id` 由工具的普通 JSON 解码忽略，见 [05](05-main-runtime.md#agent-loop-三阶段2026-11-08)。

## 只管理任务，不绑定产物

2026-11-06，用户决定先去掉所有任务与产物绑定，只保留任务记录的创建、读取、更新与状态管理。理由是先把需求登记和逐项执行做好，产物归属以后再讨论。

任务工具只保留 `list_tasks`、`record_task_input`、`update_task`。不提供结果追加工具、不建立结果表；助手消息和文件都不保存任务归属。`task_messages` 继续关联用户需求和补充来源，这是输入追溯，不是产物绑定。取消通过状态 `cancelled` 表示，不新增物理删除工具。

迁移 `00041_remove_assistant_task_binding` 删除旧 `messages.task_id`、相关索引和“可见助手消息必须有任务”的约束。历史消息正文、任务与输入关联继续保留；Down 只恢复旧结构，不猜测已经移除的回答归属。聊天实时与历史接口、前端消息类型也不再包含任务 ID。

固定指令仍要求登记与任务选择只调用工具，不发送正文；这靠模型遵守指令，后端不隐藏正文。其他正文作为独立聊天消息保存。模型继续按当前任务聚焦工作，但后端不把回答登记为任务结果，也不做产物交付检查。

## 任务怎样结束与恢复

Main 使用 `update_task` 变更当前任务的状态，入参只有 `task_id` 和 `status`。把进行中任务改回 `queued` 以先做另一项，见上文「先做更该先做的事」。模型判断要求的工作已经完成后，将状态改为 `completed`。这个操作只更新任务记录，不绑定回答或文件，也不要求先登记任何结果。进度和等待原因保留在对话中，任务表不设置 `outcome`。内部工具回执、进度消息或状态变更本身不代表结果已经交付。

需要用户澄清或外部条件暂时不满足时，Main 在调用 `update_task` 标为 `waiting` 的同一条回复里说明原因并提出必要问题，保留恢复所需的信息。其他排队任务可以继续。用户补齐条件后，登记工具将对应任务重新排队。用户明确取消时才标为 `cancelled`，新话题本身不取消旧任务。这延续此前关于受阻任务和取消语义的选择。

启动、完成或等待的 `update_task` 仍由工具说明要求单独占一批工具调用，但 2026-11-06 用户确认删除运行时的执行前批级拦截（原 `taskBatchRestrictions`）：状态合法性由 `UpdateTaskStatus` 的 SQL 条件与单活动任务唯一索引保证；混批从未在真实模型上观察到，此前仅用受控脚本响应验证过拦截，保留它属于针对未发生情况的重复防御。工具批次执行期间到达的新输入不打断已发出的批次，在下一次模型决策时登记。

## 只靠提示词与工具（2026-11-06）

同日稍后，用户指出自己从未要求在每次请求尾部添加实时任务状态，并明确任务接入只需要两样东西：固定指令中与 task tools 有关的段落，加上三个 task tools，其他都不需要。据此删除整套运行时接入：

- 删除每次请求尾部注入的 `task_context` 状态消息与 `taskContextPrompt`，请求组装恢复为「请求组装规则」原本的样子，见 [05](05-main-runtime.md#请求组装规则2026-11-02)；
- 删除 `buildTaskRequest`（原 `backend/internal/agent/tasks.go`）：后端不再在组装请求前查询当前任务、待登记输入与待办，也不再补回已被 compact 移出当前世代的未登记原话；
- 删除按阶段缩小工具范围的 `TaskInputDefinitions` 与 `TaskSelectionDefinitions`，每次请求都下发全部工具定义；
- 删除只由阶段机制设置的 `ToolOnly` 与 `RequireOutput`：登记或选择时模型若写了正文会直接可见，既无正文又无工具调用的回复重新按合法的沉默结束保存，不再补试；
- 迁移 `00042_main_work_from_messages_only` 把 `main_work` 恢复为只看最新一条消息：`queued` 或 `in_progress` 任务本身不再唤醒或续跑 Runner，一次正文回复结束后队列里即使还有任务，也要等后续消息或工具回执再次驱动；
- 当前任务状态改由模型在需要时自己调用 `list_tasks` 读取；`record_task_input` 的待登记消息 ID 改从该消息的 `current_time` 标记取得，工具内部仍按 `task_input_through_sequence` 校验下一条未登记输入；
- 测试专用的 `backend/cmd/verifyruntime` 与 `backend/cmd/verifychat` 两个命令一并删除，仓库不再保留测试代码。

保留不变的是任务表、关联表、输入登记位置、三个工具的执行逻辑与单任务的数据库约束。选择这一形态的代价是登记、选择与逐项执行的纪律只剩提示词约束：模型忘记登记、先答后登记或在队列未清空时提前交付，运行时都不再拦截。换取的是请求组装只有一份规则，任务不再有第二套运行时状态通道。

迁移 `00042` 已在本地 PostgreSQL 完成执行、回滚、再执行，并核对 `main_work` 的视图定义不再包含任务与未登记输入条件；`go build ./...` 与 `go vet ./...` 通过，sqlc 重新生成后只删除了两条不再使用的查询。按仓库约定没有新增或保留测试代码，因此没有对真实模型做任务归类质量的评测。

模型调用失败仍沿用 `main_failed_through_sequence` 停住自动重试，任务、关联消息与对话历史保留；有新输入时再次处理。进程崩溃或重启后，Manager 启动时读一次 `main_work` 恢复待办，不需要等待用户发送下一条消息。任务是否可运行仍以 `main_work` 和失败停住位置为准，见 [05](05-main-runtime.md#停机与开机2026-11-09)。

## 收尾任务提醒（2026-11-07）

2026-11-07，用户提出模型结束回答后若任务没有完成，会直接停下，要求：

> 当模型结束回答之后，如果task还存在没有被completed，就继续一轮对话，告诉模型你还有没有completed的task

触发口径经确认定为状态 `in_progress` 与 `queued`，`waiting` 不算：等待表示正卡在用户澄清或外部条件上，追问只会反复打扰。据此，Runner 在模型以无工具调用的回复收尾、原本准备结束本次运行时，先用 `ListTasks` 查一次该用户的任务；仍有进行中或排队的任务就不结束，再调用一轮模型，并在请求末尾追加一条不落库的不可见 user 消息（`name = task_reminder`，原文在 `prompt.go` 的 `taskIncompleteReminder`）：请模型先读 `list_tasks` 核对现状，工作真做完了就单独一批标 `completed` 后静默结束、不重复已交付的结果，没做完就继续做，卡住就标 `waiting` 并向用户说明，没有进行中的任务就自己选下一项排队任务启动。当前任务状态仍由模型自己读，提醒只说「还有没完成的任务」，不替模型指出是哪一项。

这部分推翻上一节「只靠提示词与工具」：后端重新读取任务状态，但只在模型收尾这一个点上读。不恢复每轮请求的 `task_context` 注入，不按阶段缩小工具范围，也不改 `main_work`——任务队列仍不单独唤醒 Runner，思考气泡、启动恢复与调度都不受影响。提醒不落库，同一段历史每次组装逐字相同，不破坏前缀缓存；压缩请求不带提醒，只有压缩后的正式请求才追加。

防重复靠 Runner 本地的一个签名：进行中与排队任务的 ID 与状态拼成的集合，集合没变时只提醒一次。只有任务集合发生变化（完成、启动或新登记一项）才允许再提醒，队列因此能一项接一项往下走，模型始终不更新状态时也不会无限多花模型调用、反复发送重复正文。每个被提醒的收尾至少多一次模型调用，这是该机制的预期成本。已经停下的运行不会被追溯唤醒，进程重启后停在已收尾消息上的用户仍等下一条消息，这与 `main_work` 只看消息尾部的既有语义一致。

实现位于 `runner.go` 的 `unfinishedTaskSignature` 与运行循环、`before_request.go` 的 `buildAgentRequest`（提醒由参数传入）与 `prepareContext` 透传（2026-11-08 按三阶段重排后的位置）；没有新增迁移、SQL 或前端改动，复用已有 `ListTasks` 查询。本地 `go build ./...` 与 `go vet ./...` 通过，按仓库约定没有新增测试，未对真实模型做任务归类质量的评测。

## 前端实时展示任务进展（2026-11-12）

2026-11-12，用户要求在聊天前端实时展示任务进展，并确认三项产品选择：

1. **展示粒度**：只展示 `tasks` 表已有的任务队列与状态流转（进行中、排队中、等待回复、已完成、已取消的标题、需求描述与更新时间），不采集实时工具调用名，也不在任务表增加子步骤字段。
2. **展示位置**：存在未结束任务时在输入框上方浮现实时进度胶囊（展示当前进行中或排首位的任务标题及剩余排队/等待项数），全部结束后自动收起、日常闲聊零打扰；同时在右上角悬浮操作栏增加带未完成数字角标的「任务进展」入口，点击胶囊或右上角按钮均打开任务进展浮层（桌面停靠右上角卡片、手机全屏展开），查看当前待办与最近结束的 30 项历史任务。
3. **只读交互**：浮层纯只读展示；补充说明、调整先后顺序或取消任务仍通过在聊天里告诉阿芒完成。选择理由是避免界面直接改库绕过对话上下文，防止模型对任务状态的认知与数据库脱节。

技术实现完全复用既有 Redis `chat:notify` 广播与聊天 WebSocket 下行通道，不新增数据库迁移、不新增独立事件游标、不修改 agent loop 三阶段：

- `after_request.go` 在每次数据库工具（含 `record_task_input`、`update_task`）事务提交后本就会调用 `r.notifyChat()` 向 Redis `chat:notify` 发布用户 ID；
- `tasks.sql` 新增专供界面读取的 `ListChatTasks`（取全部未关闭任务，加上按 `updated_at DESC` 截取的最近 30 项已关闭任务），与模型使用的 `ListTasks` 隔离，保持模型工具返回和前缀缓存零变化；
- WebSocket 在 `ready`（已登录时）、`authenticated` 与 `pushChatMessages` 发出的 `messages` 帧中顺带附上 `tasks` 快照数组，前端 `ChatController` 收到后直接整表替换内存中的 `tasks`。因为单用户的快照仅数 KB，随状态帧整表覆盖比维护独立增量游标更简单，跨实例切换、断线重连和 30 秒心跳补查天然幂等一致；输入框进度胶囊挂在 `.composer-padding` 内，由既有 `ResizeObserver` 自动同步 `--composer-height`，不遮挡列表底部消息。

## 实现取舍

目标归类需要理解用户语义，因此仍由模型判断。数据库保证单任务状态与事务提交；登记、选择与逐项执行的顺序只由提示词约束。这些约束不能证明模型对“同一目标”的判断一定正确，也不能判断回答内容是否真正满足需求。

登记通常增加一轮模型工具调用。工具定义每次全量下发且逐字不变，请求前缀不因任务状态变化。选择这一成本，是为了把未完成需求从容易遗漏的对话推断变成可恢复的持久记录。

迁移 `00034_add_tasks` 跳过最后一次普通助手收尾之前的历史输入，只登记其后尚未处理的用户消息，不回填全部历史需求。表结构见 [02 数据模型](02-data-model.md#tasks)，工具登记与执行位于 `backend/internal/agent/tools/tasks.go`。
