# 05 Main 运行时

每个用户拥有一个长期主对话 Main，并可按需并发派生多个独立上下文的异步后台 Subagent（2026-11-12 重新设计引入，见下文「异步后台 Subagent 与零损耗直通转发（2026-11-12）」）。Main 与用户之间是一条永不重置的长期对话，使用同一份 `messageList`。Main 与 Subagent 均为逻辑概念：平时不占任何进程，有活时由任意空闲的对等后端容器通过 Redis 抢占对应执行租约并启动 Runner 协程运行，处理完即释放。代码在 `backend/internal/agent/`。持久化需求队列支持多项独立任务并行处于 `in_progress`，详见 [11 需求队列](11-tasks.md)。

## 实现顺序

最小对话（含 WebSocket 收发完整消息）→ 边生成边显示 → 更多工具（`read_message`、`search_message`）→ 压缩与历史检索 → Subagent。

当前 `已实现` 的代码包含最小 Main 对话、联网 `search` / `fetch_url` / `read_image`、Web 聊天（现使用 React，移动端为 PWA）。推送完整消息与状态，不推送逐段生成的文字。

2026-10-22，用户调整近期实现顺序：先为 Subagent 添加联网 `search` 与网页读取工具，再制作 WhatsApp 风格的简版 Flutter 客户端，最后在本地联调。完成这些工作需要先实现 Main 派发任务、Subagent 独立运行及双方消息通信。边生成边显示和压缩仍属于完整交付范围；历史检索已于 2026-10-30 实现（范围与口径见 [02](02-data-model.md#历史检索-已实现)）。

## Main 的执行能力

Main 直接使用执行工具完成任务，当前包括 `search`、`fetch_url`，使用既定参数、供应商和执行代码。2026-10-23 曾确认 Main 与 Subagent 共用工具、Main 可自行决定直接执行或派发的 B 架构；该架构已于 2026-11-02 随 Subagent 一并删除，见文末「删除 Subagent（2026-11-02）」。

2026-10-30，用户改为：Main 模型生成的正文就是发给用户的消息。后端等模型整条回复生成结束后再一次性推给前端，不逐段推送；正文为空则不产生用户消息。2026-11-03 起，只有最近一次用户输入之后已经给过有效正文，才允许无正文、无工具调用地结束；否则补试一次，仍为空则显示失败，见下文「模型调用失败」。这一条取代 2026-10-23「只通过 `send_message` 回复用户、禁止直接输出正文」的旧约定。项目尚未上线，旧约定下的数据直接清空，不做兼容。

因此 Main 的每次模型回复里，正文（包括与工具调用同批的正文）都会成为一条用户消息。耗时任务要主动用正文汇报进度：动手前用一两句说明要做什么，之后每几轮工具写一句刚确认了什么、接下来做什么，计划变化或受阻时也写；进度不代替最终结果，也不重复已经说过的进度。简单问题只给结果。模型正文是对外内容，不得暴露内部推理、计划与编排细节。

2026-10-30，用户要求进度再积极一些：提示词按上面的节奏要求汇报；运行时另加兜底。Main 连续 5 个步骤只调用工具、正文为空时，在下一次模型请求的上下文末尾插入一条系统消息，请它先写一句用户能读的进度再继续，同一条回复里仍可调用工具。计数从最近一条这类提醒之后重新算起，数到用户可见正文，或用户的新输入为止。同一次沉默最多插入 3 次，避免模型把紧跟工具结果的运行时文字当成注入。提醒写入 `messages`（`role = system`），立刻占序号，之后的请求仍能看见；聊天只显示用户消息和 Main 正文，用户看不到它。压缩时按压缩前的原文判断，提醒追加在摘要之后，不写进摘要输入。ikun Gemini 会把中途系统消息并进系统指令，文字仍在，只是不留在工具结果后面；DeepSeek 保留这个位置。2026-11-02 起，这条提醒改为 `role = user`、`name = progress_reminder`、`visible = false` 的不可见消息，不再使用 system 角色，两个渠道都把它作为普通 user 消息留在上下文末尾。同日稍后，进度提醒改为组装时按轮数插入、不再落库，规则改为每 4 轮无正文工具调用一次、不设上限，见下文「运行循环」中的「请求组装规则」。

不写正文即不打扰用户。原 Agent 间通信工具 `send_message` 已于 2026-11-02 随 Subagent 删除。

### 连续消息与多个请求（2026-11-04，2026-11-06 更新）

用户确认，连续收到的消息按目标判断关系。不同目标分别处理，各自给出结果；为同一目标补充背景、约束、修正或追问的消息合并处理，按更新后的要求执行。判断依据是用户想得到什么结果，不能只看消息先后或话题是否相同。例如，先后要求解释两条不同推文需要分别回答；要求解释后补充“讲给初学者听”属于同一个请求。

新话题不自动取消旧请求，旧流程也不能遮住新问题。只有用户的语义表示取消或替换时才放弃对应请求，暂停则保留。Main 结束前核对每个未完成请求是否已给出相关结果、必要的澄清问题或具体阻塞原因。进度说明、工具结果和其他问题的答案都不算完成该请求；一个请求受阻时，继续处理不依赖它的其他请求。用户追问漏答时，要识别并回答被漏掉的问题。已完成或取消的请求不重新执行。

选择理由是避免模型沿着旧工具流程回答旧话题，或因用户换了话题而遗漏先前问题。规则写入 `MainInstructions` 与结束协议；压缩提示词也分别保留每个请求的目标、进度、暂停、阻塞与未答问题，避免摘要只留下最新话题。当时只约束模型行为，未新增任务队列。2026-11-06，用户改为用 `tasks` 登记和更新需求，另一个目标先排队，当前目标结束后再领取下一项。新实现将输入登记和任务执行分开，并以持久化队列驱动续跑，详见 [11 需求队列](11-tasks.md)。

## 运行循环 `已实现`

### Agent loop 三阶段（2026-11-08）

2026-11-08，用户要求以 agent loop 为核心做一条规定：

> agentloop里面分为请求前阶段、请求阶段和请求后阶段，我希望代码的展示能够展现出这三个阶段，这样改代码的时候比较方便，确保所有的修改都仅限于这三个阶段

用户同时指出原写法防御了很多走不到的场景，不贴合这个模型。据此重排 `backend/internal/agent/`，本节取代下文对运行循环代码结构的描述，运行语义除下列各条外不变：

- **请求前**（`before_request.go`）负责「整理状态并产出请求」：先清理上次进程退出的残留（进行中的模型调用记为中断、删除未发布的占位、未结束的步骤以中断收尾），再补跑缺回执的工具，然后开一条步骤、读设置、必要时压缩，最后按「请求组装规则」组装请求。残留清理由运行开头挪到这里，是用户的提议；它每轮执行一次，必须排在开步骤之前，因为 `FailUnfinishedSteps` 会把该用户所有未结束的步骤标为中断。
- **请求**（`request.go`）负责「发出并收回完整回复」，含模型调用日志、可取消窗口（15 秒）内被新输入打断、首段输出或满 15 秒时占位。
- **请求后**（`after_request.go`）负责「处理本轮结局」：成功就保存回复并执行其中的工具；被新输入取代就撤销占位、进入下一轮；临时故障就以错误结束这一步，退避后原样再走一轮；其余失败统一失败收尾。请求前与请求阶段的错误不在原地处理，作为本轮结局交给它。
- **循环主体**（`runner.go`）只判断还有没有活（含收尾任务提醒及其签名），按顺序调用三个阶段。原先套在主循环里的重试循环改为循环的下一轮，重试计数与十分钟预算作为跨轮状态，回复成功或被新输入取代后清零；退避间隔、次数与预算不变。
- 阶段之间只通过 `modelRequest` 与 `chatResponse` 交接；修改 agent loop 前先说明属于哪个阶段，修改循环主体须单独确认。这条规则写入 `AGENTS.md`。Go 同一个包内没有文件级访问隔离，所以边界靠文件划分与这条规则维持，不拆子包；拆子包要导出大量类型并逐层传依赖，与「尽可能少的抽象」冲突。

同日逐项讨论后确认的取舍：

- **新输入打断**：用户在 A（保持现状）、B（请求前占位、请求中不取消，补充留到下一轮）、C 中选择 C：保留模型思考时被新输入取消重来，但只在占位事务里检查一次新输入，删除登记思考请求之后的那次补查。组装之后、登记之前到达的输入仍由占位事务兜住，只是放弃得晚一些。
- **临时数据库错误**：删除 Manager 对临时数据库错误的退避重试、启动读待办的退避循环与 `retry.go`。理由是这属于 `AGENTS.md` 禁止的「中间层自行恢复」，自用单实例下很少发生。现在按普通失败收尾：数据库已恢复时聊天显示失败、重发即可；收尾也写不进去时只记日志，等下一条消息或重启；启动时读不到待办则进程退出，由部署的重启策略拉起。
- **压缩请求的工具定义**：不再复用上次成功 Main 请求的供应商原文，也不再跨渠道转换，改为与普通请求相同的 `tools.Definitions()`，由各渠道按同一套转换发出；`providers.Request.ProviderTools` 与 `GetLastContextUsage` 的 `provider_tools` 列一并删除。理由是复用原文是为了在按阶段缩小工具范围时保持前缀一致，该机制已于 2026-11-06 取消，现在每次 Main 请求都发全部工具，同一套转换得到的字节相同。唯一差别是部署改了工具定义后的第一次压缩用新定义，这时缓存本就会失效一次。本条取代下文 2026-11-06「工具定义复用上次成功 Main 请求的供应商原文」。
- **收尾任务提醒的签名**保留不动：模型被提醒后完全可能不更新任务，签名防止无限续跑；改成「每次运行只提醒一次」会漏掉模型推进到下一项后又忘记标完成的情况。
- **删除走不到的检查**：发请求前的配对检查 `validateRequestMessages`（组装只会接上存在的回执，缺回执的工具在组装前已补跑），重复调用 ID 的去重（供应商不会返回重复 ID，每个调用只写一条回执），`executeDatabaseTool` 里永远进不去的 `OutsideTransaction` 分支，保存回复时的「占位消失」检查（占位只有当前 Runner 会动），`requestMessage` 解析失败时的兜底，以及删除旧任务绑定字段 `source_message_id` 与 `related_message_ids` 的一百多行清理代码（任务工具用普通 JSON 解码，模型照旧例多传的字段会被忽略）。运行开头的 `HasMainWork` 不是重复检查而保留：没有它，一次空唤醒会在模型没运行时触发收尾任务提醒。

首段非空白正文或首个工具调用分片到达时，Runner 在用户消息写入锁内检查请求快照之后是否还有输入。有则放弃旧请求，无则插入一行不可见的 `generating` assistant 占住对话位置。供应商继续生成，整条回复完整后更新同一行并结束 step。纯思考不会占位；合法的沉默结束也要做同样的输入检查。用户可以在生成和工具执行期间继续发送消息，工具参数完整并落库后才执行，下一次模型决策会读取期间到达的输入。这样较晚完成的回复不会掩盖它从未读过的消息。

生成中的行不参与上下文组装；它在 `main_work` 中仍属于待处理工作。重启后 Runner 的请求前阶段先清理上次中断的占位并重读消息。模型失败时若已有超出本次输入范围的新消息，失败记录保留在步骤中，Main 继续处理新输入。完整正文的推送和断线补齐见 [消息与实时通信](04-messaging.md)。

**2026-11-12 更新：思考可取消窗口限定为 15 秒。** 用户指出模型已经思考较长时间后再被新消息取消重来会白白丢掉已投入的推理与等待，经结合 IM 话语切分（Utterance Chunking）实证研究（紧邻拆句连发集中在 2–5 秒，66.9% 的连续发送在 10 秒内，轮次响应中位数约 15 秒）确认将可取消窗口定为 15 秒（`thinkingCancelWindow = 15s`，仅改请求阶段 `request.go`）：

- **15 秒内且尚未产出正文或工具**：沿用原有打断逻辑，新消息到达即取消当前请求、把相邻补充合并进新请求重发；若 15 秒内已产出首段输出，则立即执行占位事务并停止监听打断。
- **满 15 秒仍在纯思考**：定时器触发与首段输出共用的同一次幂等占位事务（`sync.Once`），在 `lockAndVerifyLease` 锁内最后核对一次前 15 秒是否已有漏网新输入，无则插入 `generating` 隐藏占位行并清空 `thinking` 取消句柄。
- **满 15 秒之后**：不再因新消息取消当前请求；由于占位行已在第 15 秒入库，此后到达的新消息在数据库序号与聊天 `position` 上都排在本次回复之后，模型完成本轮思考并更新该占位行后，下一轮循环自动读取期间到达的新消息继续处理，既保住深度思考成果，也不会让旧回复排到未读过的新消息后面。

- 消息入库即分配 `sequence`，不再有「`sequence` 为空即待读」这一状态；迁移时把遗留的待读行按 `id` 顺序补号，再把列改为非空。
- Main 要不要运行只看最新一条消息（视图 `main_work`）：最新一条是 user 消息、工具回执，或带工具调用的 assistant 消息，就有活要干；是没有工具调用的 assistant 消息，就表示 Main 已经停下。扫描、唤醒和聊天的思考气泡都用这同一个判断。
- 失败后停住靠 `users.main_failed_through_sequence`：运行失败收尾时记下当时的最大序号，`main_work` 排除最新消息序号不超过它的用户，直到用户新消息带来更新的消息才再试。没有已读状态后，若不记这个位置，同一条失败的消息会被每次扫描反复重试。进程崩溃不写这个标记，重启后由启动恢复从持久状态接着做。
- `steps` 只记录：每次模型调用尝试一条，压缩一条。普通 step 与对应的 assistant 消息在同一事务里结束，工具回执带上这条 step 的 ID；`steps.model_reply` 删除，崩溃后不复用旧回复，直接按消息尾部决定下一步。

选择理由：事实只有一份，就是数据库里那串消息。不必再另外维护「读到哪了」和「哪一步没做完」来推断要不要运行，出问题时对照消息表就能看出 Main 处于什么位置；请求本身也只是这串消息按固定规则展开的结果。

2026-11-03，用户决定 Runner 只认 PostgreSQL 通知：删掉每秒扫描与启动时的自发唤醒，也删掉 WebSocket 保存消息后与 Runner 跑完一轮后的进程内直接唤醒；一切唤醒只能由 LISTEN 收到的 `user_messages` 与 `main_input` 通知转发，Main 写回仍靠事务里的 `NOTIFY`。Runner 被唤醒后照旧全量扫描 `main_work`，所以任何一条通知都会顺带捡起此前遗漏的工作。用户接受随之而来的语义变化：消息与运行状态不会丢，但触发可以丢——进程重启或 LISTEN 断线间隙里错过的通知不重放，遗留工作要等下一次通知才恢复、不保证恢复时间，本节此前「通知只减少等待，漏通知不会使任务永久无人处理」的说法就此作废。选择理由是调度只保留一条事件路径，不再让周期轮询与多处直接唤醒并存。

### 请求组装规则（2026-11-02）

Runner 被唤醒后按下面的规则把消息展开成请求；固定指令、时间和提醒在组装时注入，不注入任务状态，不自动加载记忆文件：

1. 第一条是由代码提供的固定指令，以不可见 user 消息（`name = instructions`）注入，不落库。指令说明 `/memories/memory.md` 是核心约定和主题索引，需要时通过 `memory` 先读根、再读相关主题；根正文不拼入固定指令，也不另存自动快照消息。
2. 其后是最新摘要与之后的全部消息，按 `sequence` 排列，逐条只删前端展示字段。工具回执不按入库位置排，而是紧跟它的 assistant 消息、按调用顺序排列（每个调用只写一条回执，2026-11-08 起不再去重）。这样工具执行期间进来的用户消息会排在这批回执之后，供应商要求的「调用之后紧跟回执」不会被打断。根与主题均由工具按需读取；查询排除旧原型 `memory_context` 自动快照，保留主动读取记忆产生的正常工具回执，见 [02](02-data-model.md#主题记忆)。
3. 每条用户本人发的消息（`sender = user`）后面紧跟一条不可见 user 消息（`name = current_time`），时间取这条消息自己的 `created_at`（UTC）。2026-11-04 起同条标记附上这条消息的固定 ID，方便定位用户原话；文件式 memory 工具不要求模型提交来源 ID。
4. 进度提醒：从最近一条用户消息起计数，每出现一轮没有可见正文的工具调用就加一，满 4 轮在该轮回执之后插一条不可见 user 消息（`name = progress_reminder`）并重新计数；Main 写出可见正文或用户发来新消息也重新计数；不设次数上限。用户选择的是「写了正文就重新计数」：提醒的目的就是让用户隔一段时间能听到进展，Main 已经开口说明它没有沉默，没必要再催。
5. 2026-11-08 起发出前不再另做检查：缺回执的工具在请求前阶段组装之前已补跑，只有还有活时才会组装请求，所以「每个工具调用都有回执、最后一条不是已结束的 assistant」由流程本身保证，见上文「Agent loop 三阶段」。

时间、来源 ID 和提醒都由消息本身算出：时间来自入库时刻，ID 来自消息主键，提醒位置来自轮数，所以同一段历史每次组装结果逐字相同，供应商的前缀缓存不受影响。原来落库的指令行、当前时间行与提醒行由 `00026` 删除，回滚迁移只恢复结构，不恢复这些行。

2026-11-05，用户确认 Gemini 渠道改为按来源角色保留工具回执与新输入的边界：同批 `tool` 回执仍合并成一条原生 `role = user` 消息，紧接的用户输入另起一条 `role = user`，其后的时间标记仍与该输入合并；其他相邻同来源角色的消息沿用原有合并规则。理由是同一历史请求的真实模型对照中，原组装再次只回答旧问题，拆分后续接工具链则回答了两题。此次只调整消息边界，不保证回答顺序或分成两次回复；对照中模型先答新问题、再答旧问题，合在一条正文里。

### 对等多实例调度与停机交接（2026-11-11）

2026-11-11，用户决定将项目改造为**单机多后端容器部署**，并在对比工业界主流方案后，明确对齐 **LangSmith Deployment（Data Plane）模式**：「无状态对等后端容器 + PostgreSQL 保存 100% 持久事实 + 纯内存 Redis 只传瞬时信号与临时租约」。选择理由是：同一台阿里云服务器运行两个对等 Go 容器（`api-1`、`api-2`）与一个 `redis:8-alpine` 容器不增加任何额外云主机或云数据库成本，却能解决单容器发布更新时的全站断连问题，同时为将来跨机扩容或逐段流式推送留好标准边界。本节取代下文 2026-11-09 的单进程调度说明。

1. **职责边界与零持久负担的 Redis**
   - PostgreSQL 仍是唯一业务持久事实来源（大文件与原图持久保存在私有 OSS）；Redis 显式以 `--save "" --appendonly no` 纯内存模式运行，仅负责实时信号、临时租约与以 `oss://` 为键的旁路图片缓存，不存任何唯一持久状态，即使 Redis 重启清空也不会丢失业务数据。
   - **竞争唤醒队列（`agent:wake_queue`）**：`Wake` 通过 Lua `LPOS + RPUSH` 将 `user_id` 去重入队（不维护独立 Set，避免极端强杀留下不一致状态）；各容器先占用本机 `slots` 并发槽位再调用 `BLPOP`，本机满载时自动让其他空闲容器取活。
   - **每用户临时租约（`agent:lease:<user_id>`）**：抢到任务后执行 `SET NX EX 30` 写入随机令牌，运行期间后台协程每 10 秒通过 Lua 核对令牌续期；租约被取代或超期失联时立即取消本机 Runner。
   - **跨实例思考打断（`agent:input` Pub/Sub）**：新输入提交后广播 `<user_id>:<sequence>`，所有容器订阅该频道，仅正在运行该用户 Runner 的容器命中本机内存字典 `runners[userID]` 并调用 `newInput(sequence)` 取消未占位思考。
   - **5 秒周期补偿**：每 5 秒扫描 `ListMainWork`，补发本地打断并将当前无 Redis 租约的待办重新推入队列，兜底启动恢复、Redis 重启与瞬时网络抖动。
2. **PostgreSQL 栅栏代数（Fencing Token）与三阶段边界**
   - 仅靠 Redis 临时锁不足以防范极端 GC/IO 停顿后的脑裂覆盖。迁移 `00052_add_user_lease_epoch` 在 `users` 表新增单调递增的 `main_lease_epoch`：容器抢到 Redis 租约后，在 `LockUserMessages` 锁内确认待办并原子 `+1` 取得本轮代数。
   - 遵循三阶段规定并经用户确认修改 `runner.go`：`Runner` 持有本轮 `leaseEpoch` 并提供固定锁序的 `lockAndVerifyLease`（永远先拿 `LockUserMessages` 再核对 `main_lease_epoch`，消除死锁可能）；请求前阶段（清理上次中断残留、开步骤、开压缩步骤与保存摘要）、请求阶段（首段输出占位 `reserve`）和请求后阶段（放弃尝试、保存回复、保存工具回执与失败收尾）的所有写库事务均核对该代数，步骤结束查询同步限定 `finished_at IS NULL`。一旦发现代数已被新实例推进，旧 Runner 立即返回 `errLostLease` 静默退出，不覆盖新实例数据，也不写入 `main_failed_through_sequence`。
3. **滚动停机秒级交接**
   - 容器收到 `SIGINT` / `SIGTERM` 后：HTTP 最多等 5 秒关闭；Manager 立即取消本地正在运行的 Runner（延续 2026-11-09 确认的「信号一到立即取消、接受重复请求与重复执行成本」原则），协程退出后主动删除自己持有的 Redis 租约，并复查 `HasMainWork` 将未完用户推回 `agent:wake_queue`，另一个存活容器在毫秒级内接手从数据库断点继续。

### 停机与开机（2026-11-09，单进程阶段历史记录）

后端是单进程调度：进程内唯一的 `Manager` 在消息提交或定时投递后由 `Wake` 直接唤醒 Runner，同一用户同一时间只有一个 Runner。用户在 2026-11-09 说明理由：

> 改成单进程是因为目前就只有我一个人用，我希望等日后用户量上来了再改成多实例

即当前只有维护者一人使用，单进程足够，跨进程的执行归属、心跳与接管只增加复杂度；用户量上来后再考虑多实例。同日用户确认文档按单实例迭代，删除此前多实例方案的全部说明，以后需要时再重新设计。

**停机。** 收到 `SIGINT` 或 `SIGTERM` 后：

- HTTP 服务停止接受新连接，最多等 5 秒让普通请求结束，随后恢复默认信号处理，再发一次信号即立即退出。已升级的 WebSocket 不归 `http.Server.Shutdown` 管理，进程退出时直接断开，前端按既有逻辑重连并按游标补齐；这几秒内这些连接仍可发消息，消息落库后在重启后处理。
- 定时调度器随信号停止，投递中的事务回滚，到期安排在重启后再投。
- Manager 随同一信号取消正在运行的 Runner，模型请求和工具调用一起停下，等这些协程退出后关闭连接池。信号到达后不再开新的 Runner。没写完的模型调用、占位和步骤留在数据库里。生产 compose 的 `stop_grace_period` 为 20 秒，协程未退出就强制结束。
- 因进程退出而中断的运行不写失败位置 `main_failed_through_sequence`。重启后照常继续。

**开机。** 连接池不预先连接数据库，HTTP 立即监听，`/healthz` 反映数据库状态。Manager 启动时读一次 `main_work`，逐个唤醒有活的用户；读取失败则进程退出，由部署的重启策略拉起，生产 compose 等数据库健康后才启动后端。之后不再周期扫描待办。Runner 的请求前阶段先清理残留（进行中的模型调用记为中断、删除未发布的占位、未结束的步骤以中断收尾），再补跑缺回执的工具，然后照常请求。停机期间错过的一次性安排照常投递，周期安排合并为一次。

**可靠性优先于费用与重复执行。** 信号一到就取消进行中的模型请求和工具调用，重启后重新请求；执行到一半的联网工具会再执行一次。用户在 2026-11-09 确认接受重复费用与重复执行，原话：

> 多花钱/多执行没有关系，这是保证可靠性的cost

同日确认停机不再留十五秒：重启会从数据库原地继续，多等一会儿并不能多保住已经落库的结果。可靠性由每一步先落库、重启后补做缺的部分来保证，恢复只有这一条路径；被切断的调用只多花费用，不影响结果。这条把 2026-10-28「用重复执行的成本换取恢复逻辑简单、任务不丢」（见上文「崩溃重做」）从崩溃扩展到正常停机。本节依据代码核对写成，没有另做运行验证。

### 模型调用（流式接收、整条推送）

## 异步后台 Subagent 与零损耗直通转发（2026-11-12）

2026-11-12，用户要求在一次性收到多条可并行任务时让阿芒具备并行处理能力以提高吞吐量，并在审阅工业界实践（Anthropic Research、Claude Code、OpenAI Agents SDK、Cognition「并行贡献智力、单线程执行写入」、OpenClaw 异步完成投递与 LangChain `forward_message` 防转述损耗实验）后逐项确认以下设计，取代 2026-11-02 删除 Subagent 的状态（迁移 `00055_add_subagents`）：

1. **异步后台并发与自动完成投递（抛弃旧版 `send_message` 工具）**
   - Main 通过数据库工具 `spawn_subagent(title, prompt)` 在用户消息事务内原子创建 `subagents` 记录与首条指派消息，提交后推入独立的 Redis 队列 `agent:subagent_wake_queue`；Main 可以在同一轮并发启动多个 Subagent 后立即结束本轮，运行期间用户随时发来新消息 Main 均能秒级接手继续并行，无队头阻塞。


已确认的规则：

- Subagent 与 Main 之间只有消息，没有单独的“汇报”类型：Subagent 用 `send_message` 发消息给 Main，进度与结果都只是消息内容。
- `subagents.status` 由运行时维护，不依赖消息内容。Subagent 因错误无法继续时，运行时向 Main 的列表写入一条 `sender = system`、`sender_subagent_id` 为该 Subagent 的通知。
- Subagent 停下后再收到 Main 的消息，会被重新唤醒继续工作；无论上次是 `idle` 还是 `failed`，收到消息都会唤醒，`failed` 只表示上一次因错误停下。
- 暂不提供强制中断（无 `cancelled` 状态、无 `stop_subagent` 工具）：让 Subagent 停下靠 Main 发消息；卡住或长时间运行的情况由之后的超时规则兜底，超时中断后状态为 `failed`。

用户在 2026-10-22 确认以下运行限制：

- 每个用户最多同时执行 3 个 Subagent，超出的任务保留在数据库中排队，已有任务结束后继续执行。上限按用户划分，避免一个用户一次派发大量任务占满执行资源。
- 每个 Subagent 每次被唤醒后最多连续执行 15 分钟。超时后标为 `failed`，由运行时通知 Main。之后收到 Main 的新消息仍可重新唤醒，避免持续出错或未结束的任务无限占用并发名额。

调度使用每用户三个 PostgreSQL 会话锁名额，跨实例共享上限；排队由 `idle` 与待读消息表示，不新增状态取值。`subagents.started_at` 保留本轮开始时间，重启不会重置截止时间。调度、失败通知、恢复和再唤醒已通过真实 PostgreSQL 隔离 schema 测试，外部接口在该测试中模拟。

### read_image `已实现`

2026-11-09，用户要求参考 aether-start 增加 `read_image(url)`，并明确数据库只保存图片地址，base64 只在发送时生成。

工具下载一张直接的 HTTP 或 HTTPS 图片地址，不读取网页正文。地址不能带账号密码；最多跟随 3 次跳转，每一跳仍须是不带账号密码的 HTTP(S)。连接前解析域名，只拨公网地址，拒绝本机、内网和链路本地地址，也不走环境代理。单次请求 30 秒。响应不看 `Content-Type`，用现有的 `ValidateBytes` 认真实字节，只接受 PNG、JPEG、GIF 和 WebP，单张不超过 4 MB。

校验通过后写入该用户的 OSS 前缀 `aether-chat/<user_id>/`。成功回执是一条原生 `tool` 消息，`content` 为两段：一段文本记下原始网址、MIME 类型和字节数，一段 `image_url` 的 `url` 是 `oss://`。失败仍存成 `Error: ...` 字符串。其他工具的回执继续是字符串。

发送前仍由 `ResolveMessages` 把 `oss://` 读出并换成 data URL，OpenRouter 原样收到文本段加 `image_url`。ikun Gemini 把文本放进 `functionResponse.response.output`，把图片放进 `functionResponse.parts` 的 inline data。压缩用的 Claude 已能把内容数组里的 `image_url` 放进 `tool_result`。base64 只出现在发出的请求和模型调用日志里。聊天界面不展示工具回执，因此前端不改。

固定指令和 `fetch_url` 的说明要求图片用 `read_image`。实现位于 `backend/internal/agent/tools/read_image.go`。

此协议曾自 2026-10-30 起只适用于 Subagent（已于 2026-11-02 随 Subagent 删除）：它收到 `send_message` 的 `delivered` 回执后不得重复发送相同消息；当前工作已交付或等待已派发任务时，通过无工具调用的私有 `[DONE]` 标记结束回合，该标记保留在其内部上下文，不会显示在用户消息流中。运行时仍根据真实已提交工具回执判断交付，标记本身不能替代给 Main 发送结果。此协议解决部分新模型无法稳定以空回复结束、进而重复调用发送消息工具的问题。Main 不再使用该标记：正文即用户消息，不写正文即结束。
