# 05 Main 运行时

每个用户只有一个 Main（2026-11-02 起系统只有 Main，没有 Subagent），与用户之间是一条永不重置的长期对话，使用同一份 `messageList`。Main 是逻辑概念：平时不占任何进程，最新一条消息需要它处理时，某台后端获取该用户的 Main 锁后运行它，处理完即释放。代码在 `backend/internal/agent/`。

## 实现顺序

最小对话（含 WebSocket 收发完整消息）→ 边生成边显示 → 更多工具（`read_message`、`search_message`）→ 压缩与历史检索 → Subagent。

当前 `已实现` 的代码包含最小 Main 对话、联网 `search` / `fetch_url`、Web 聊天（现使用 React，移动端为 PWA）。推送完整消息与状态，不推送逐段生成的文字。

2026-10-22，用户调整近期实现顺序：先为 Subagent 添加联网 `search` 与网页读取工具，再制作 WhatsApp 风格的简版 Flutter 客户端，最后在本地联调。完成这些工作需要先实现 Main 派发任务、Subagent 独立运行及双方消息通信。边生成边显示和压缩仍属于完整交付范围；历史检索已于 2026-10-30 实现（范围与口径见 [02](02-data-model.md#历史检索-已实现)）。

用户原话：

> 我希望给用户发的消息添加这么几个状态：sending，delivered，read；main 先用 haiku5.5；系统提示词就参考 anthropic 发布过的 blog 和我们的产品理念；模型调用失败，无需对用户显示任何内容，内部上报。

## Main 的执行能力

Main 直接使用执行工具完成任务，当前包括 `search`、`fetch_url`，使用既定参数、供应商和执行代码。2026-10-23 曾确认 Main 与 Subagent 共用工具、Main 可自行决定直接执行或派发的 B 架构；该架构已于 2026-11-02 随 Subagent 一并删除，见文末「删除 Subagent（2026-11-02）」。

## Main 如何回复用户

2026-10-30，用户改为：Main 模型生成的正文就是发给用户的消息。后端等模型整条回复生成结束后再一次性推给前端，不逐段推送；正文为空则不产生用户消息。2026-11-03 起，只有最近一次用户输入之后已经给过有效正文，才允许无正文、无工具调用地结束；否则补试一次，仍为空则显示失败，见下文「模型调用失败」。这一条取代 2026-10-23「只通过 `send_message` 回复用户、禁止直接输出正文」的旧约定。项目尚未上线，旧约定下的数据直接清空，不做兼容。

因此 Main 的每次模型回复里，正文（包括与工具调用同批的正文）都会成为一条用户消息。耗时任务要主动用正文汇报进度：动手前用一两句说明要做什么，之后每几轮工具写一句刚确认了什么、接下来做什么，计划变化或受阻时也写；进度不代替最终结果，也不重复已经说过的进度。简单问题只给结果。模型正文是对外内容，不得暴露内部推理、计划与编排细节。

2026-10-30，用户要求进度再积极一些：提示词按上面的节奏要求汇报；运行时另加兜底。Main 连续 5 个步骤只调用工具、正文为空时，在下一次模型请求的上下文末尾插入一条系统消息，请它先写一句用户能读的进度再继续，同一条回复里仍可调用工具。计数从最近一条这类提醒之后重新算起，数到用户可见正文，或用户的新输入为止。同一次沉默最多插入 3 次，避免模型把紧跟工具结果的运行时文字当成注入。提醒写入 `messages`（`role = system`），立刻占序号，之后的请求仍能看见；聊天只显示用户消息和 Main 正文，用户看不到它。压缩时按压缩前的原文判断，提醒追加在摘要之后，不写进摘要输入。ikun Gemini 会把中途系统消息并进系统指令，文字仍在，只是不留在工具结果后面；DeepSeek 保留这个位置。2026-11-02 起，这条提醒改为 `role = user`、`name = progress_reminder`、`visible = false` 的不可见消息，不再使用 system 角色，两个渠道都把它作为普通 user 消息留在上下文末尾。同日稍后，进度提醒改为组装时按轮数插入、不再落库，规则改为每 4 轮无正文工具调用一次、不设上限，见下文「运行循环」中的「请求组装规则」。

不写正文即不打扰用户。原 Agent 间通信工具 `send_message` 已于 2026-11-02 随 Subagent 删除。

### 连续消息与多个请求（2026-11-04，2026-11-06 更新）

用户确认，连续收到的消息按目标判断关系。不同目标分别处理，各自给出结果；为同一目标补充背景、约束、修正或追问的消息合并处理，按更新后的要求执行。判断依据是用户想得到什么结果，不能只看消息先后或话题是否相同。例如，先后要求解释两条不同推文需要分别回答；要求解释后补充“讲给初学者听”属于同一个请求。

新话题不自动取消旧请求，旧流程也不能遮住新问题。只有用户的语义表示取消或替换时才放弃对应请求，暂停则保留。Main 结束前核对每个未完成请求是否已给出相关结果、必要的澄清问题或具体阻塞原因。进度说明、工具结果和其他问题的答案都不算完成该请求；一个请求受阻时，继续处理不依赖它的其他请求。用户追问漏答时，要识别并回答被漏掉的问题。已完成或取消的请求不重新执行。

选择理由是避免模型沿着旧工具流程回答旧话题，或因用户换了话题而遗漏先前问题。规则写入 `MainInstructions` 与结束协议；压缩提示词也分别保留每个请求的目标、进度、暂停、阻塞与未答问题，避免摘要只留下最新话题。当时只约束模型行为，未新增任务队列。2026-11-06，用户改为用 `tasks` 登记和更新需求，另一个目标先排队，当前目标结束后再领取下一项。新实现将输入登记和任务执行分开，并以持久化队列驱动续跑，详见 [11 需求队列](11-tasks.md)。

## 运行循环 `已实现`

**2026-11-03 更新：运行中补充输入。** 用户消息提交后，PostgreSQL 的 `main_input` 通知携带用户和输入序号。持有 Main 执行锁的实例如果仍在等首包或只收到思考分片，就取消旧请求，重新读取上下文，相邻补充可以进入同一次新请求。相同客户端消息重发没有新插入，也不会触发取消。

首段非空白正文或首个工具调用分片到达时，Runner 在用户消息写入锁内检查请求快照之后是否还有输入。有则放弃旧请求，无则插入一行不可见的 `generating` assistant 占住对话位置。供应商继续生成，整条回复完整后更新同一行并结束 step。纯思考不会占位；合法的沉默结束也要做同样的输入检查。用户可以在生成和工具执行期间继续发送消息，工具参数完整并落库后才执行，下一次模型决策会读取期间到达的输入。这样较晚完成的回复不会掩盖它从未读过的消息。

生成中的行不参与上下文组装；它在 `main_work` 中仍属于待处理工作。接管执行锁的实例先清理上次中断的占位并重读消息。模型失败时若已有超出本次输入范围的新消息，失败记录保留在步骤中，Main 继续处理新输入。完整正文的推送和断线补齐见 [消息与实时通信](04-messaging.md)。

2026-11-02，用户认为原有 IM 运行架构不够简洁，要求改为：

> 1.每当有user message进来的时候，先保存进数据库，然后"唤醒"一个runner 2.每当一轮多次工具调用返回所有结果后，先保存进数据库，然后"唤醒"一个runner 3.runner被唤醒之后，只需要负责按照规则组装。4.组装规则：- 第一个是main prompt，然后是message表里上一个compact到最新的所有message，且每个工具都有对应的调用结果，最新的message是user message。- 然后每隔四轮工具调用，插入一句invisible user message（progress）- 每个visible user message的后面都要插入invisible user message （时间）

同日用户又要求「把已读什么的状态去掉」。据此 `messages` 表成为 Main 运行状态的唯一来源，本节取代此前由「待读补号 + 未完成 step」驱动的循环（迁移 `00026_derive_main_work_from_messages`）：

- 消息入库即分配 `sequence`，不再有「`sequence` 为空即待读」这一状态；迁移时把遗留的待读行按 `id` 顺序补号，再把列改为非空。
- Main 要不要运行只看最新一条消息（视图 `main_work`）：最新一条是 user 消息、工具回执，或带工具调用的 assistant 消息，就有活要干；是没有工具调用的 assistant 消息，就表示 Main 已经停下。扫描、唤醒和聊天的思考气泡都用这同一个判断。
- 失败后停住靠 `users.main_failed_through_sequence`：运行失败收尾时记下当时的最大序号，`main_work` 排除最新消息序号不超过它的用户，直到用户新消息带来更新的消息才再试。没有已读状态后，若不记这个位置，同一条失败的消息会被每次扫描反复重试。进程崩溃不写这个标记，重启后等下一次通知触发扫描时从消息尾部接着做。
- `steps` 只记录：每次模型调用尝试一条，压缩一条。普通 step 与对应的 assistant 消息在同一事务里结束，工具回执带上这条 step 的 ID；`steps.model_reply` 删除，崩溃后不复用旧回复，直接按消息尾部决定下一步。

选择理由：事实只有一份，就是数据库里那串消息。不必再另外维护「读到哪了」和「哪一步没做完」来推断要不要运行，出问题时对照消息表就能看出 Main 处于什么位置；请求本身也只是这串消息按固定规则展开的结果。

2026-11-03，用户决定 Runner 只认 PostgreSQL 通知：删掉每秒扫描与启动时的自发唤醒，也删掉 WebSocket 保存消息后与 Runner 跑完一轮后的进程内直接唤醒；一切唤醒只能由 LISTEN 收到的 `user_messages` 与 `main_input` 通知转发，Main 写回仍靠事务里的 `NOTIFY`。Runner 被唤醒后照旧全量扫描 `main_work`，所以任何一条通知都会顺带捡起此前遗漏的工作。用户接受随之而来的语义变化：消息与运行状态不会丢，但触发可以丢——进程重启或 LISTEN 断线间隙里错过的通知不重放，遗留工作要等下一次通知才恢复、不保证恢复时间，本节此前「通知只减少等待，漏通知不会使任务永久无人处理」的说法就此作废。选择理由是调度只保留一条事件路径，不再让周期轮询与多处直接唤醒并存。

2026-11-03，用户进一步要求「一个实例可以跑多个 runner，每个用户对应一个 runner」。据此原全局 Runner 拆为进程内唯一的 `Manager` 与每用户一个的 `Runner`：Manager 持有连接池、模型客户端、工具与服务配置等共享依赖和全局并发名额，被通知唤醒后全量扫描 `main_work`，为每个还没有 Runner 的用户创建一个 Runner 并登记；Runner 只服务自己这一个用户（用户 ID 与思考中请求的取消句柄都存在它自己身上，不再用全局 map 按用户存），抢该用户的 Main 咨询锁后按消息尾部运行，结束时先由 Manager 注销、再释放并发名额。Runner 只在有活时存在，不为无活用户常驻协程，共享依赖也不按用户复制；同一用户在本实例只有一个 Runner，跨实例仍靠 PostgreSQL 咨询锁保证只跑一处。运行语义（只认通知、失败停住位置、连接预算）与拆分前完全一致。选择理由是每用户的状态与执行归到各自对象上，调度与执行的职责分开，后续单用户能力有明确落点；消息表仍是唯一事实来源，Runner 对象只是临时执行者。

```mermaid
    TAIL -->|最后一条是 user 或工具回执| CALL["按规则组装，事务外调用模型<br/>临时错误最多重试 3 次"]
```

获取锁后先清理生成中占位并收尾上次崩溃：仍在进行中的模型调用记为中断，`finished_at` 为空的 step 记为失败（「interrupted before the step finished」），然后循环：

1. 读取最新摘要与之后的全部消息。最后一条 assistant 消息若还有工具调用没有回执，执行这些工具（规则见第 4 条），回执齐全后回到本步。
2. 否则最后一条不是 assistant 时需要回复。每次尝试先创建一条 step，检查自动压缩条件，必要时生成摘要；随后按「请求组装规则」组装最新摘要与未被覆盖的消息。模型、提示词和可用工具只服务 Main。压缩的约定是干净的输入输出：消息列表与模型配置（模型、容量、输出上限、阈值）作为已确定的输入；压缩时用一条不可见 user 指令限定只生成摘要，把待压缩范围按原角色、顺序和内容原样发给同一模型（不对原上下文做任何处理），再在末尾追加一条「请压缩你的上下文、进入下一段对话」的指令，模型返回的一条摘要即替代这段历史。压缩请求明确禁止调用任何工具：保留上次成功 Main 请求的工具声明，并分别用 OpenRouter 的 `tool_choice: "none"` 与 ikun Gemini 的 `functionCallingConfig` 模式 `NONE` 明确禁用；因为 2026-10-30 一次真实压缩中，模型顺着历史里的工具轨迹输出了 `fetch_url` 工具调用和空正文，空正文被当作摘要落库后，Main 随即看不到被摘要覆盖的历史。除压缩模型调用本身失败外不考虑其他失败状态——待总结历史超过压缩模型容量、摘要为空或带工具调用或被截断、压缩后没变小或仍超限等状态，都依上游约束判定为不可达，不写对应的分块、校验、递归和复核处理。模型调用失败时返回错误，原始消息不动。2026-10-28 用户先确认干净输入输出，后改为全部压缩（不保留最后一条），均经「写代码前的预期核对」，见 [01](01-overview.md#写代码前的预期核对)。
2026-10-31，用户要求在 compact 的系统提示词中明确禁止任何工具调用。压缩请求因此先放一条独立系统指令，限定模型只输出摘要正文，不生成函数调用、不继续历史任务、不回答用户；历史消息、工具调用和回执只作为总结材料。待压缩历史仍原样保留，末尾的摘要要求和协议层禁用工具设置继续使用。理由是普通用户消息里的「不要调用工具」曾未被供应商遵守，需在系统指令中明确压缩身份与输出职责。同日，用户要求参考 Anthropic 官方的续接摘要提示词，末尾压缩指令改为五部分：目标与要求、当前进展、发现与决定、下一步、必要背景。要求保留最新请求与修正、确切约束、决定理由、失败经验、来源标识及未完成承诺，区分用户授权与代理建议、已完成与未验证、事实与推断；任务已结束时明确写出，不假定还有待办，不恢复已取消或被替代的工作。理由是摘要要让下一段对话准确接续，而非平均缩短历史，减少重复工作和丢失约束。参考 [Anthropic 默认摘要提示词](https://platform.claude.com/docs/en/build-with-claude/context-editing#default-summary-prompt) 与 [自定义压缩指令](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand#write-your-own-summarization-prompt)，按 personal agent 的聊天、联网研究和 Subagent 场景改写，输出仍为普通摘要正文。本次只修改本地提示词，未部署或修复已存在的生产空摘要。2026-11-03，用户要求去掉摘要正文的 token 上限：此前压缩指令末尾会追加 `Keep the summary text below N tokens`，N 为 `max(128, min(2048, 压缩阈值/8))`，默认阈值下是 2048。现不再附加这句，摘要长短只由上面的续接要求决定，不再按阈值折算一个数字去截。

其他要点：

- **处理中收到新消息**：按本节 2026-11-03 规则，纯思考阶段取消并重读；已占位或正在执行工具时，在本批结束后重读。工具回执在请求中紧跟其调用。
- **释放后重新调度**：释放执行锁时发出的 NOTIFY 会再次唤醒扫描，因此本次运行期间因并发名额已满被跳过的用户通常随之被捡起；数据库锁仍是跨实例执行权的依据。
- **释放失败**：释放锁出错时关闭该数据库连接，由数据库释放锁，避免带着锁回到连接池。
- **只认通知**：没有启动扫描与周期扫描（2026-11-03 决定，见上文）。进程重启或 LISTEN 断线期间遗留的工作，等下一次通知触发全量扫描时顺带恢复，不保证恢复时间。
- **连接预算**：`DATABASE_MAX_CONNS` 默认 20、最小 5。每实例最多同时运行“连接池上限减 4”个 Agent，为登录、消息和扫描保留连接。每个 Agent 的全部数据库操作使用自己持有的连接，避免持锁时再等待池中另一条连接。WebSocket 的专用 LISTEN 连接通过 Hijack 移出池，实际数据库连接预算需另加这一条，并计入所有实例的合计。
- **锁连接失效**：等待外部请求时每 5 秒检查锁连接，失效即取消请求；完成网络操作后只有仍持锁的连接能提交结果。
- **崩溃重做**：assistant 消息与 step 同事务落库，所以崩溃时要么整条回复都在、要么都不在。回复不在就重新调用模型；回复在就按回执核对工具：有回执的跳过，没有的重新并行执行。数据库工具的执行与回执同事务提交，不会重复生效；联网工具在保存回执前崩溃会被重跑，可能重复计费或产生重复副作用。2026-10-28 用户确认接受这一取舍：用重复执行的成本换取恢复逻辑简单、任务不丢。运行失败收尾时，会给最后一条助手消息中尚缺回执的工具调用补一条中断回执，避免历史里留下没有回执的工具调用，再记下失败位置。

### 请求组装规则（2026-11-02）

Runner 被唤醒后按下面的规则把消息展开成请求；固定指令、时间、提醒和实时任务状态在组装时注入，不自动加载记忆文件：

2. 其后是最新摘要与之后的全部消息，按 `sequence` 排列，逐条只删前端展示字段。工具回执不按入库位置排，而是紧跟它的 assistant 消息、按调用顺序排列，同一调用有多条回执时只取一条。这样工具执行期间进来的用户消息会排在这批回执之后，供应商要求的「调用之后紧跟回执」不会被打断。根与主题均由工具按需读取；查询排除旧原型 `memory_context` 自动快照，保留主动读取记忆产生的正常工具回执，见 [02](02-data-model.md#主题记忆)。
3. 每条用户本人发的消息（`sender = user`）后面紧跟一条不可见 user 消息（`name = current_time`），时间取这条消息自己的 `created_at`（UTC）。2026-11-04 起同条标记附上这条消息的固定 ID，方便定位用户原话；文件式 memory 工具不要求模型提交来源 ID。

- 失败写入对应 `steps.error` 并由 `slog.Error` 记录；每次请求尝试单独记一步。2026-11-03，用户确认耗尽补试后应明确显示失败，替代原先只记内部错误的约定。聊天底部显示“回复失败，请再发一条消息重试。”，不展示供应商错误或内部细节。提示根据数据库中 Main 的失败位置恢复，刷新或重连后仍可见，新输入到达后清除。
- 2026-11-03，线上 ikun Gemini 曾返回 HTTP 200、`STOP`，但正文只有换行。用户确认修复空白回复：空格与换行不算正文；最近一次用户输入之后还没有有效正文时，无正文且无工具调用的结果记为 `invalid_response`，保留实际用量和原始响应，最多自动补试一次。已经给过用户正文的工具流程仍可安静结束。选择理由是区分有效答复与协议成功，避免用户的问题被空白结果直接收尾。补试仍与本轮其他尝试共用十分钟预算，不循环生成。
- 2026-10-30，用户要求模型请求超时改为 10 分钟，与联网工具分开，并限制重试总时间。模型使用独立 HTTP 客户端，单次请求最多 10 分钟；联网工具保留 120 秒。原因是长上下文和高推理请求可能接近或超过原来的两分钟上限，不应因此过早取消并重复生成。
- 临时性错误（网络错误、超时、限流 429、服务端 5xx）最多重试 3 次，间隔为 1、2、4 秒。每轮模型调用从上下文准备开始计时，包含可能触发的压缩、全部尝试和退避，共用 10 分钟总预算；重试不重置截止时间。预算耗尽即取消请求并结束本轮，数据库收尾使用独立于该预算的上下文；模型请求日志保留实际耗时并记为传输失败。若进程退出先发生，仍按外部中断处理。独立发起的压缩请求同样使用模型客户端的 10 分钟单次上限。
- 失败收尾时若已有请求未覆盖的新输入，则继续调度；否则记下当时的最大序号，Main 停住不再重试；失败前的消息留在上下文中，用户下次发消息时，Main 会一并看到之前未回复的消息。

## Subagent（已于 2026-11-02 删除，以下为历史记录）

```mermaid
sequenceDiagram
    participant Main
    participant DB as PostgreSQL
    participant Sub as Subagent

    Main->>DB: assign_subagents：插入 subagents 行，任务说明作为其列表第一条消息
    Main-->>Main: 立即得到 subagent_id，继续工作
    DB->>Sub: 异步启动（独立上下文，后台执行）
```

已确认的规则：

- Subagent 与 Main 之间只有消息，没有单独的“汇报”类型：Subagent 用 `send_message` 发消息给 Main，进度与结果都只是消息内容。
- `subagents.status` 由运行时维护，不依赖消息内容。Subagent 因错误无法继续时，运行时向 Main 的列表写入一条 `sender = system`、`sender_subagent_id` 为该 Subagent 的通知。
- Subagent 停下后再收到 Main 的消息，会被重新唤醒继续工作；无论上次是 `idle` 还是 `failed`，收到消息都会唤醒，`failed` 只表示上一次因错误停下。
- 暂不提供强制中断（无 `cancelled` 状态、无 `stop_subagent` 工具）：让 Subagent 停下靠 Main 发消息；卡住或长时间运行的情况由之后的超时规则兜底，超时中断后状态为 `failed`。

用户在 2026-10-22 确认以下运行限制：

- 每个用户最多同时执行 3 个 Subagent，超出的任务保留在数据库中排队，已有任务结束后继续执行。上限按用户划分，避免一个用户一次派发大量任务占满执行资源。
- 每个 Subagent 每次被唤醒后最多连续执行 15 分钟。超时后标为 `failed`，由运行时通知 Main。之后收到 Main 的新消息仍可重新唤醒，避免持续出错或未结束的任务无限占用并发名额。

调度使用每用户三个 PostgreSQL 会话锁名额，跨实例共享上限；排队由 `idle` 与待读消息表示，不新增状态取值。`subagents.started_at` 保留本轮开始时间，重启不会重置截止时间。调度、失败通知、恢复和再唤醒已通过真实 PostgreSQL 隔离 schema 测试，外部接口在该测试中模拟。
