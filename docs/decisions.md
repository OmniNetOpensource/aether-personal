## 协作约束

- 技术实现由开发者判断；仅产品决策询问用户，一次讨论一个问题。用户在 2026-10-22 明确用此规则替代此前“任何微决策先询问”的要求，原话为“不要问我这种技术问题，问我产品决策问题就行”。
- 用户没说改就不要改：先核对现状、汇报结论与建议，等用户明确说改后再动代码或文档。用户在 2026-10-29 明确更新此协作方式，详见 [01](wiki/01-overview.md#本地开发)。
- 交付范围是整张架构图的全部内容。
- 实现逻辑时同时考虑 dev 和 prod 环境。
- 变量名称必须直观，禁止使用抽象的变量名。
- 写代码时，每个小模块（文件、类型、函数／方法、组件，以及函数内可独立理解的一段逻辑）前须写一两句注释，说明它负责什么、为什么存在，方便人类顺着注释逐个模块阅读；注释不逐行复述代码。用户在 2026-10-28 明确要求记下此规则，详见 [01](wiki/01-overview.md#代码注释)。
- 每个手写源文件第一行写文件头注释，一两句说清文件职责；改文件时职责变了就同步更新文件头。范围不含 sqlc 生成代码、历史迁移与 JSON 等文件。用户在 2026-10-28 确认此范围，详见 [01](wiki/01-overview.md#代码注释)。
- 完成需求时不再列出可能的报错和失败状态、交由用户确认哪些走得到。用户在 2026-10-30 取消 2026-10-28 建立的「写代码前预期核对」。失败处理由开发者按编码原则判断；2026-11-06 改为不做防御性编码、错误逐层向上抛，由最外层统一记录并决定如何呈现。详见 [01](wiki/01-overview.md#写代码前的预期核对)。
- 上下文压缩（compact）预期：干净的输入输出——消息列表与模型配置作为已确定的输入，独立的不可见 user 指令限定只生成摘要（不使用 system 角色），待压缩范围原样加一条压缩指令发给同一模型，输出的一条摘要即替代这段历史；除模型调用本身失败外，不考虑其他失败状态，不为不可达状态（待总结历史超过压缩模型容量、摘要不合格、压缩后没变小或仍超限等）写处理；阈值触发只看上一次同模型成功请求的官方 `prompt_tokens`，本地不估算 token，接受触发慢一拍。用户在 2026-10-28 确认并改为全部压缩；2026-10-30 修正为只保留 token 阈值触发（不再等闲置 6 小时），达到阈值且恰好是 Main 的用户新消息触发时只压其之前的全部历史、保留这条消息原文，其余唤醒仍全量压缩；2026-10-30 另确认压缩请求禁止调用任何工具（2026-11-06 改为保留上次 Main 的工具声明，只禁用调用，以保留前缀复用条件）；2026-10-31 追加独立 compact 系统指令，限定只输出摘要、不得生成工具调用或继续历史任务，并参考 Anthropic 的续接摘要，将内容组织为目标、进展、发现与决定、下一步及必要背景，明确区分完成状态与授权范围；2026-11-03 去掉摘要正文的 token 上限（原先 `max(128, min(2048, 阈值/8))`，默认 2048），不再在压缩指令末尾限制字数，详见 [05](wiki/05-main-runtime.md)。
- 禁止写任何测试文件。用户在 2026-10-23 明确要求记下此规则。
- 提交时采用小规模、自包含的 commit。用户在 2026-10-23 明确要求记下此规则。
